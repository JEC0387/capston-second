# 개인 데이터 인증 전환 (P0)

개인 DB API는 이제 `Authorization: Bearer <접속 토큰>`이 필요합니다. `X-Device-Id`만으로는 옷장·사진·체형·취향·백업 데이터를 읽거나 바꿀 수 없습니다. 접속 토큰과 복구 코드는 각각 256비트 무작위 값이며 서버에는 SHA-256 해시만 저장합니다. 앱은 이를 비공개 저장소에 보관하고 Android 자동 백업에서 제외하며 HTTPS에서만 전송합니다.

## 운영 적용 전

이 브랜치는 운영 DB와 Railway에 적용하지 않았습니다. 운영자 승인 후 먼저 `005_auth_credentials.sql`을 적용하고, 개인정보 API가 인증 없는 요청을 거절하는지 확인한 다음 `AUTH_REGISTRATION_ENABLED=true`를 설정해야 합니다. 앱과 서버를 서로 다른 버전으로 배포하면 기존 앱의 서버 백업은 동작하지 않습니다. 사진·체형 숫자 등 폰의 로컬 기록은 지워지지 않습니다.

## 새 설치와 복구

- 새 설치는 첫 동기화 또는 백업 화면 진입 시 빈 계정을 발급받습니다. 복구 코드를 안전하게 보관해야 다른 폰에서 복원할 수 있습니다.
- 새 폰에서 복구 코드를 입력하면 기존 접속 토큰은 폐기됩니다. 복원 전에는 동기화를 멈춰 새 폰의 대기열이 기존 기록을 덮지 않도록 합니다. 복원 중 오류가 나면 로컬 기록을 덮지 않고 다시 시도합니다.
- 코드 분실 시 서버 기록의 자동 복원은 보장하지 않습니다. 폰 안의 기록은 계속 사용할 수 있습니다.

## 기존 기기 번호 데이터

기존 `device_id`와 서버의 사용자·옷장·사진·체형 기록은 그대로 둡니다. 이전 앱 설치는 자동 동기화를 멈추고 두 선택지를 보여 줍니다.

1. 기존 서버 기록을 이전하려면 운영자가 **기기 번호 외의 독립적인 증빙**으로 소유권을 확인합니다. 확인 방법과 승인 기록은 운영 절차로 별도 정해야 합니다. 확인 후 운영자가 비공개 환경에서 `python auth_admin.py --device-id <옛 기기 번호> --verified-out-of-band`로 24시간짜리 일회용 승인 코드를 발급해 사용자에게 안전하게 전달합니다. 승인 코드는 저장소·로그·공개 채팅에 넣지 않습니다. 앱에서 승인 코드를 입력하면 새 인증을 기존 사용자 행에 연결하고, 기존 행과 데이터는 이동·삭제하지 않습니다. 복원을 마치기 전에는 동기화가 재개되지 않습니다.
2. 사용자가 이 폰의 로컬 기록으로 새 계정을 명시적으로 시작할 수 있습니다. 예전 서버 데이터는 귀속·삭제되지 않으며, 새 계정에 로컬 기록을 올리는 선택입니다.

옛 기기 번호만으로 승인 코드를 발급하면 안전한 소유권 확인이 **아닙니다**. 독립적 확인 절차가 마련되지 않았다면 레거시 클라우드 이전은 보류해야 합니다. 운영 DB 변경·승인 코드 발급·실제 배포는 별도 승인 후 수행합니다.


## 2026-10-25 후속 보안 변경 (별도 개발 브랜치)

- 운영 변경은 수행하지 않았다. 출시 전 승인된 환경에서 `005_auth_credentials.sql` 다음에
  `006_auth_hardening.sql`을 적용한다. 006은 사용자 데이터에 손대지 않고 인증 시도 제한과
  이전 승인 메타데이터만 추가한다. 기존 미기록 티켓은 교환을 거절한다.
- 신규 등록은 접속 피어당 15분 10회, 복구/이전은 각각 20회로 제한한다. 예산은 DB에서
  원자적으로 갱신해 여러 프로세스가 공유하며 실패한 요청도 차감한다. 임의
  `X-Forwarded-For`는 신뢰하지 않는다. Railway가 모든 요청을 같은 프록시 피어로
  전달하면 예산이 공유될 수 있으므로 출시 전 신뢰 프록시 설정을 실제 환경에서 검증한다.
  원시 IP나 토큰은 제한 표에 저장하지 않으며 24시간 지난 행은 다음 인증 요청에서 정리한다.
- 전체 사용자 통계 `/api/stats/overview`, `/api/recommendations/stats/all`,
  `/api/product-interests/popular`에는 별도 운영자 Bearer 인증을 요구한다.
  `ANALYTICS_ADMIN_TOKEN_SHA256`에는 256비트 이상 무작위 운영자 토큰의 SHA-256만 설정한다.
  개인 접속 토큰은 전체 통계를 열 수 없다. 평가 스크립트 전체 통계는
  `FASHION_ANALYTICS_ADMIN_TOKEN`, 개인 통계는 기존 `FASHION_AUTH_TOKEN`을 사용한다.

### 기존 데이터 소유권 확인과 승인 기록

1. 이전 담당자와 승인 담당자는 기기 번호만을 증빙으로 인정하지 않는다. 저장된 이메일,
   기존 계정 인증 수단, 이전에 확인된 서명 키 등 독립적으로 신뢰할 수 있는 자료와
   신청자의 권한을 대조한다. 옷 사진 내용, 추측 가능한 기록, 기기 번호만의 일치는 불충분하다.
2. 신뢰할 수 있는 자료가 없으면 이전을 보류하고 원본을 보존한다. 새 계정 시작은 앱에서
   사용자가 명시적으로 선택한다. 운영자는 임의로 다른 사람의 계정을 연결하지 않는다.
3. 승인 기록은 접근 제한된 운영 기록에 신청/확인 시각, 확인 방법, 검증자, 대상 사용자,
   승인자, 근거 자료 참조, 전달/폐기 이력을 남긴다. DB에는 검증자 식별자와 승인 기록
   참조, 확인 방식, 발급/소비 시각만 남긴다. 원본 증빙이나 복구 코드는 기록하지 않는다.
4. 별도 승인 후에만 비공개 터미널에서 다음 형태로 발급한다. 예시는 실행하지 않았다.

   ```text
   python auth_admin.py --device-id <기존번호> --verified-out-of-band \
     --approved-by <운영자ID> --approval-reference <승인기록참조> \
     --verification-method verified-account-record
   ```

   기존 설치 서명으로 확인했다면 `signed-installation-challenge`를 쓴다. 입력값은 실제
   확인을 대신하지 않는다. 발급자는 확인 자료와 승인 기록의 유효성을 책임지고 검토한다.
5. 코드는 확인된 신청자와의 비공개 채널에서 한 번만 전달한다. 공개 채팅/이슈/로그에
   붙이지 않는다. 기본 만료는 24시간이며 재발급 시 기존 미소비 티켓은 모두 무효화된다.
   동시 교환은 사용자/티켓 행 잠금 및 계정 고유 제약으로 한 계정만 성공한다.
6. 스테이징에서 구 앱의 401 안내, 새 앱의 이전 선택, 네트워크 단절 후 이어하기를 검증한
   후에만 서버·앱 출시를 승인한다. 등록은 기본 비활성 상태를 유지한다.

### Android 저장 및 복원

- 토큰·복구 코드·인증 상태를 Keystore AES-GCM으로 암호화한다. 기존 평문은 암호문 저장과
  같은 preferences 커밋에서 제거한다. 키 접근/복호화 실패는 자료를 지우거나 새 계정을
  만들지 않고 명시적인 복구를 기다린다. 암호문과 임시 복원 preferences는 자동 백업에서 제외한다.
- 서버 주소가 바뀐 경우 이전 토큰의 서버 바인딩을 유지한다. 복구 응답이 실패해도
  이전 토큰을 새 서버에 다시 묶지 않는다. HTTP 리다이렉트는 따르지 않는다.
- 계정 변경은 업로드 배치와 직렬화한다. 복구/이전 요청 전에 동기화 중단을 내구성 있게
  저장하고, 원격 스냅샷과 모든 사진을 확보한 뒤 로컬 교체를 준비한다.
- 교체 전 `noBackupFilesDir/restore-original-<시각>.json`에 기존 preferences와 미전송
  대기열을 보존한다. 기존 사진은 삭제하지 않는다. `restore-journal.json`은 앱 시작 시
  모든 저장소에 다시 적용되므로 설치 중 종료돼도 부분 교체 상태로 동기화하지 않는다.
  저널 설치 후 앱을 다시 시작해야 동기화가 재개된다. 이 안전 복사본은 개인정보를 포함하므로
  앱 전용 영역에서만 관리하고 운영 로그/저장소/자동 백업으로 복사하지 않는다.
- 디스크 고장/공간 부족으로 저널 적용에 실패하면 저널과 원본을 보존한다. 강제 삭제로
  우회하지 말고 저장 공간/기기 상태를 해결한 후 재시작한다. 실기기 강제 종료와
  Keystore 접근 상실 검증은 JVM 테스트와 별도로 필요하다.
