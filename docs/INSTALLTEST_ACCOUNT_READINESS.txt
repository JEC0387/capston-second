FashionFit 18617 — 내일 실기기 인증 준비

범위
- com.jeiu.fashionproject.installtest 전용. 기존 18616과 동일한 독립 debug 서명을 사용한다.
- 기존 DataAuth/옷장/백업/계정 복구/Google·카카오 자격증명을 변경하거나 복사하지 않는다.
- 이번 개발에서는 운영 계정 등록, 운영 DB 변경, Genlook 요청, 사진 전송을 수행하지 않는다.
- 새 APK 설치 및 실제 시험 계정 등록은 담당자의 별도 승인/준비 뒤 수행한다.

1. 진단과 개선
2026-11-09 실측: DB 상태 API는 14.281초 후 ready/syncReady/authReady=true,
authProtocol=2를 반환했다. 5초 제한에서는 5.157초 후 시간 초과했다.
ServerSettings는 기존 5초 읽기 제한 대신 비동기 OkHttp를 사용한다.
서버 식별 /는 전체 8초, /api/health/database는 전체 25초가 상한이다.
두 요청은 순차로 최대 약 33초; 호출 취소 시 네트워크도 취소한다.
각 요청 connect timeout=3초, 응답 32KiB 제한, 자동 재시도/redirect 없음.
UI 메인 스레드에서 네트워크를 실행하지 않는다. 서버 응답 지연 자체를 고쳤다는 뜻은 아니다.

서버 담당 황상윤 확인 사항:
- DATABASE_URL 연결 대상/리전/RTT, pool checkout/pre_ping, 각 SELECT/rollback 시간을 비밀정보 없이 계측.
- database_status는 최초 body_measurements 검사와 _SCHEMA_CHECKS 각각을 순차 실행하고
  총 14회 engine.connect()를 사용한다. 왕복 지연 누적은 코드상 후보이며 원격 계측 전 확정하지 않는다.
- 반환된 ready 값은 정상이다. 임의 마이그레이션 재실행·DB_AUTO_CREATE 활성화는 금지.
- 향후 서버 최적화 시 검사를 생략하거나 ready를 강제하지 말고, 실제 검사 결과와 기한을 유지해야 한다.

2. 시험 계정 연결 설계
기존 installtest DataAuth.ensureReady의 자동 등록 차단은 유지한다.
새 InstallTestAccount는 기존 DataAuth와 별도 암호화 저장소 installtest_account를 사용한다.
Android Keystore AES-GCM으로 저장하고 저장소별 AAD로 다른 vault의 암호문 전용을 차단한다.
이 저장소는 Android 자동 백업 및 기기 이전에서도 제외한다.
이 계정은 AI 서버 세션에만 사용한다. DbSync, 기존 기록 복원, 소셜 계정 전환에는 연결하지 않는다.
앱 시작/화면 진입/연결 확인은 새 계정을 자동 생성하지 않는다.
앱 종료 후에는 저장 토큰을 바로 신뢰하지 않고 상태 GET 확인을 거쳐야 한다.

관리자 선행 조치 (이 문서나 APK 제작이 실행 승인을 대신하지 않음):
1) 사용할 HTTPS 서버, DB 준비 상태 및 실제 배포 SHA를 확인한다.
2) 빈 독립 시험 계정 1개 생성에 대한 사람의 승인과 승인 번호를 기록한다.
3) 기존 /api/auth/register는 AUTH_REGISTRATION_ENABLED=true일 때만 등록을 허용한다.
   담당자가 기존 운영 정책과 영향 범위를 확인해야 한다. 이번 작업은 이 설정을 변경하지 않는다.
   이 플래그는 서버 전체 등록 허용이며 특정 승인 번호를 암호학적으로 검증하는 기능이 아니다.
   UI 승인 번호는 로컬 감사 기록이다. 서버별/사용자별 승인이 검증됐다고 자동 주장하지 않는다.
4) 운영 등록 허용이 부적절하면 승인된 격리 서버를 준비한다. 인증 우회나 기존 토큰 복사는 하지 않는다.

승인 후 사용자 순서:
1) 마법봉 화면의 '관리자 승인 시험 계정 연결'을 연다.
2) 표시된 HTTPS 서버 주소를 관리자와 대조한다. 승인 번호만 입력한다(키/비밀번호/토큰 입력란 없음).
3) 관리자 승인 확인 체크 → '새 시험 계정 만들기' → 확인창의 '승인된 계정 생성'.
4) POST /api/auth/register {legacyPending:false} 1회로 새 빈 계정만 만든다.
   기존 사용자 기록이나 사진은 요청에 포함하지 않는다. 기존 계정 연결/가져오기를 하지 않는다.
5) 서버의 201 응답을 암호화 저장하고 GET /api/auth/status의
   authenticated=true, dataEnabled=true를 확인한 경우에만 시험 세션이 준비된다.
6) '연결 확인 · 다시 확인'으로 /api/outfit-vton/config를 조회한다.
   승인된 계정과 서버의 ready/정책 조건이 충족되기 전까지 생성은 차단된다.
7) 앱을 다시 실행하면 '시험 계정 인증 확인'으로 GET 검증 후 설정을 다시 조회한다.

실패 처리:
- 등록 전에 암호화된 시도 기록을 남긴다. 중복 탭은 Mutex 및 UI로 차단한다.
- 503/401/네트워크 실패/취소/응답 유실/프로세스 종료 시 자동 재등록하지 않는다.
- 결과가 불명확하면 관리자에게 승인 번호와 시각을 전달해 서버 감사 기록을 확인한다.
  현재 API에는 등록 idempotency key/시도 번호 조회가 없으므로 앱에서 안전한 자동 복구를 보장할 수 없다.
  앱 데이터 삭제나 기록 초기화로 재시도하지 않는다. 명시적인 별도 복구 검토가 필요하다.
- 발급 서버와 현재 서버가 다르면 토큰을 보내지 않는다. redirect에도 인증정보를 전달하지 않는다.
- 보안 저장소 실패 시 기존 파일을 지우거나 키를 교체하지 않는다.
- 기존 DataAuth의 일반 백업 상태 표시는 별도 계정의 상태이다. 시험 계정 연결이 옷장 백업을 켜지 않는다.

3. Genlook 및 내일의 검증 범위
이번 작업의 Genlook 호출/사용 크레딧/사진 전송은 0이다.
계정 준비만으로 Genlook 준비 또는 생성 성공이라고 판정하지 않는다.
운영 담당자는 OUTFIT_VTON_ENABLED/DEPLOYMENT_APPROVED/PROVIDER,
정책·보관·저장소, GENLOOK_ENABLED/DEPLOYMENT_APPROVED/PRIVACY_APPROVED/
PAID_CALLS_APPROVED/PREPAID_CONFIRMED/AUTO_TOPUP_DISABLED_CONFIRMED,
키 존재, 승인 검토 ID·비용 상한·원장 영속성을 확인해야 한다. 비밀값을 공유하지 않는다.
실제 생성은 별도 사진/비용 승인이 있는 때에만 진행한다.
Google·카카오의 별도 패키지·인증서 등록 문제는 이 시험 계정 기능으로 우회하지 않는다.

내일 읽기 중심 검사:
- 기존 앱을 삭제하지 않고 installtest 패키지/서명/versionCode를 비교한 뒤 승인된 업데이트.
- 기존 옷장·사진·배치·저장 결과가 유지되는지 확인.
- 연결 진단 중 화면 반응, 기한 초과, 취소/뒤로가기 확인.
- 등록 승인 전에는 새 계정/사진/AI 요청이 발생하지 않는지 확인.
- 승인된 시험 계정 등록 및 GET 확인은 위 담당자 선행 조건이 준비된 뒤 별도 수행.
- 서버 준비/실제 인증/실제 생성/실제 기기 결과를 구분해 기록한다.
